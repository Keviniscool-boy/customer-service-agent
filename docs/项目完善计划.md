## 3. 其他异常处理

### 3.1 模型接口失败或超时

原问题：

```text
模型调用异常会直接抛出，用户只能看到 Python 错误。
失败过程中留下的聊天消息还可能影响下一次请求。
```

解决方式：

- 捕获模型普通调用异常
- 捕获结构化输出解析异常
- 删除本次失败请求留下的消息
- 返回固定的降级回复
- 降级回复不伪造答案，也不保存错误上下文

降级回复：

```text
当前服务暂时不可用，请稍后再试。
```

### 3.2 RAG 没有结果

原问题：

```text
检索不到内容时只返回 []，模型可能看不懂，甚至自己编答案。
```

解决方式：

- 空问题直接返回失败
- 检索结果低于 `0.35` 相似度时，认为没有可靠答案
- 没有结果时返回 `success: false`
- Embedding 或索引异常时返回“知识库暂时不可用”
- 限制 `top_k` 在 1 到 5 之间

### 3.3 转人工

原问题：

```text
requires_human 以前只是 True/False，不会真正产生任何记录。
```

解决方式：

- 新增 `create_handoff()`
- 生成 `HUMAN-XXXXXXXX` 格式的工单号
- 工单状态保存为 `pending_human`
- 写入 `sessions/handoff_tickets.json`
- 客服回复中显示工单号

这还是学习版 mock 工单，后面可以替换成真实客服系统或数据库。

## 4. 对话显示和转人工逻辑

### 发现的问题

订单不存在时曾出现：

```text
已为你转人工，工单号：HUMAN-E4D4B88D。
意图: order_query
置信度: 99%
转人工: 是
追问: 您是否确认订单号及下单账号无误，并需要我为你转人工？
人工工单: HUMAN-E4D4B88D
```

这里有两个问题：

- 已经创建工单后，又继续询问是否需要转人工
- 意图、置信度、转人工状态等内部字段直接显示给用户

### 解决方式

转人工状态改成互斥：

```text
需要确认：requires_human=false + follow_up_question 有内容 + 不创建工单
已经转人工：requires_human=true + 创建工单 + follow_up_question 为空
```

具体修改：

- 有追问时，不创建人工工单，并把 `requires_human` 改为 `false`
- 追问内容合并到客服回复中，不显示“追问：”标签
- 工单创建成功后清空 `follow_up_question`
- `main.py` 只显示客服回复，不显示意图、置信度、转人工状态和内部字段
- 工单号保留在客服自然语言回复中，方便用户查看
- 读取旧会话时重新注入最新系统提示词，避免旧的“小夕”继续生效

### 追加日志：会话文件编码问题

品牌替换后第一次完整测试发现：

```text
JSONDecodeError: Unexpected UTF-8 BOM
Ran 8 tests ... FAILED
```

原因：PowerShell 重写 `sessions/session.json` 时加入了 UTF-8 BOM，但 `storage.py` 只按纯 `utf-8` 读取。

解决：

- `load_messages()` 改用 `utf-8-sig` 读取，兼容有 BOM 和无 BOM 的 JSON
- 重新保存 `sessions/session.json`，去除 BOM

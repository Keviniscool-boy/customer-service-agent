### 做了什么

### 两个容易混的东西

```text
SYSTEM_PROMPT           告诉模型应该怎么做
CustomerServiceResponse 规定模型要返回哪些字段
```

### `EcomAgent` 是什么

自己定义的电商 Agent 类，不是 OpenAI 自带的。

它里面保存：

- 模型客户端
- 模型配置
- 提示词
- 对话历史

`__init__`：创建 Agent 时初始化这些东西。

`chat()`：接收用户问题，调用模型，返回 AI 的结构化回答。

`reset()`：清空聊天记录，但保留提示词，重新开始对话。

### 当前流程

```text
用户问题 → Prompt + 历史消息 → 模型 → 结构化答案
```

### 遇到的问题

- `CustomerServiceResponse` 不能写成 Enum，要用 `BaseModel`。
- `SYSTEM_PROMPT` 是字符串，不能写成类。
- 测试时要确认使用的是当前项目的 `.venv`。

# MCP 学习记录

## MCP Server

- MCP 是让 Agent 和工具服务按统一协议通信的方式。
- 原来：`chat.py -> registry.py -> order.py`。
- 现在：`MCP Client -> MCP Server -> order.py`。
- `server.py` 没有重写订单查询，只是用 `@mcp.tool()` 公开已有的 `query_order()`。
- MCP 2.0 使用 `MCPServer`，旧教程里的 `FastMCP` 已不存在。
- 服务地址：`http://127.0.0.1:9123/mcp`。
- 浏览器直接打开 `/mcp` 出现 `Missing session ID` 是正常的，因为它没有按 MCP 流程初始化会话。

## 下一步

写 MCP Client：连接 Server，读取并调用它公开的工具。

## MCP Client 和 Agent 接入

- `mcp_client/client.py`：负责连接 MCP Server、发现工具、调用工具。
- `mcp_client/converter.py`：把 MCP 工具格式转换成模型能看懂的 OpenAI tools 格式。
- `chat.py`：启动时连接 MCP，把 MCP 工具和本地工具合并给模型。
- 模型需要调用工具时，`chat.py` 根据工具名分流：MCP 工具走 MCP Client，本地工具走 `registry.py`。
- 当前 `query_order` 走 MCP；物流、商品、退款仍然走本地工具。

### 当前流程

```text
用户问题 → chat.py → 模型判断
                   ├─ 本地工具 → registry.py
                   └─ MCP 工具 → MCP Client → MCP Server
```

### 遇到的问题

- MCP 2.0 返回两个连接对象，不能按旧版的三个对象解包。
- MCP 2.0 的工具字段是 `input_schema`，不是旧版的 `inputSchema`。
- 本地 MCP 请求被系统代理转发会返回 502，所以 Client 使用 `trust_env=False`。

### 已验证

- MCP Client 能发现 `query_order`。
- MCP Client 能调用 `query_order` 并拿到订单数据。
- `EcomAgent` 能同时加载本地工具和 MCP 工具。

## CRUD 和 SQLite

Agent 里的工具经常会操作数据：

- 查询订单、物流、商品：Read
- 创建退款申请、人工工单：Create
- 修改退款状态、会话摘要：Update
- 删除会话：Delete

现在聊天记录保存在 `sessions/session.json`。JSON 适合学习和单个会话，但用户多了以后不方便按用户、会话查询。

SQLite 是一个本地数据库文件。升级后可以把多个用户、多个会话、每条消息统一保存到数据库里，再根据 `user_id` 和 `session_id` 读取上下文。

当前 JSON 记忆流程：

```text
chat.py → messages → session.json
```

SQLite 记忆流程：

```text
chat.py → sessions/messages 表 → app.db
```

学习顺序：先做两张表：

- `sessions`：保存会话和摘要
- `messages`：保存用户消息和客服回复

之后再把 `chat.py` 里的 `load_messages()`、`save_messages()` 换成数据库读写。

### 已完成：保存完整消息

修改了 `agent/database.py`：

- `messages` 表增加 `message_json` 字段。
- 旧的 `app.db` 启动时会自动补这个字段。
- `save_message()` 现在接收完整消息字典。
- `load_messages()` 优先恢复 `message_json`，兼容旧数据。
- 普通消息和包含 `tool_calls` 的消息都可以保存和读取。

实际测试结果：

```text

普通消息和工具调用消息读取成功

```

说明：当时数据库模块已经支持完整消息；后续 `chat.py` 已完成 SQLite 接入，当前 Agent 使用 `data/app.db` 保存会话，JSON 文件仅作为旧备份保留。

### 已完成：chat.py 接入 SQLite

`chat.py` 现在：

- 启动时初始化 SQLite 表。
- 根据 `user_id` 找到最近会话，没有就创建新会话。
- 从 `messages` 表恢复聊天记录。

## 统一错误处理

之前不同错误的返回格式不一样：有的返回 `detail`，有的只有字符串。现在统一成：

```json
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "会话不存在"
  }
}
```

已处理：

- 未登录：`401 UNAUTHORIZED`
- 没有权限：`403 FORBIDDEN`
- 资源不存在：`404 NOT_FOUND`
- 参数错误：`422 VALIDATION_ERROR`，并带 `details`
- 未预期异常：`500 INTERNAL_SERVER_ERROR`

真实请求验证：

```text

返回 401
{"success":false,"error":{"code":"UNAUTHORIZED","message":"未提供认证信息"}}
```

中间发现“没有 Token”被误判成“Token 无效”，已拆开处理。

结果：`21` 个测试全部通过，编译检查通过。

## 订单状态和退款流程

```text

```

用户可以取消自己的“待发货”订单，不能取消已经发货的订单。已发货订单的状态应该由物流或后台服务推进。

- 重复申请：拒绝，不重复创建记录。

这只是退款申请和审核状态记录，还没有连接真实支付退款接口。

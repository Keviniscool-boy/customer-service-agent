## 2026-08-20：阶段 1，Agent 配置化基础

### 做了什么

- 新增 `config/agent_config.py`，定义 `AgentConfig` 配置模型。
- 配置了 Agent 名称、角色、欢迎语、语气、服务范围、知识库目录、启用工具、模型和温度。
- 新增 `configs/agents/ecommerce.json`，作为默认电商 Agent 配置。

### 遇到的问题和解决方法

- 默认配置如果同时写在 Python 和 JSON 中，后续容易出现两份内容不一致。
- 已改为由 `configs/agents/ecommerce.json` 作为默认配置来源，Python 只负责读取和校验。

### 当前状态

阶段 1 完成。配置已经接入 `EcomAgent` 的模型参数和工具开关，默认配置下 1.0 行为保持不变。

## 2026-08-20：阶段 2，Prompt 模板化

### 遇到的问题和解决方法

- 旧提示词文件换行格式和补丁上下文不一致，第一次修改没有应用。
- 已拆成新增生成器、替换兼容文件、接入 `chat.py` 三步处理，并重新跑完测试。

### 当前状态

阶段 2 完成。默认电商 Agent 的 Prompt 内容保持原有业务规则，自定义配置会生成不同角色的 Prompt。

## 2026-08-20：阶段 3，工具可插拔基础

### 做了什么

- 新增 `ToolRegistry`，统一保存工具定义和实际 Python 函数。
- `EcomAgent` 支持注入自己的工具注册表，并根据 `enabled_tools` 过滤工具。
- 用户绑定工具的 `user_id` 注入逻辑移动到注册表中。
- 保留 `TOOL_DEFINITIONS`、`TOOL_FUNCTIONS` 和 `execute_tool()` 作为 1.0 兼容入口。

### 为什么这样做

工具不应该继续全部写死在 `chat.py`。Agent 只需要声明启用哪些工具，注册表负责找到定义和执行函数，后面增加新工具不会继续扩大核心流程的分支。

### 遇到的问题和解决方法

- 直接删除旧注册入口会影响 1.0 的调用方式。
- 新注册表和旧入口同时保留，旧代码可以继续执行，新代码可以注入独立注册表。

### 验证结果

- 新增工具注册表测试 3 个，通过。
- 全部测试共 47 个，通过。
- `compileall` 通过。

### 当前状态

阶段 3 的基础完成。工具已经可以注册、筛选和注入，但工具权限确认规则还要在安全阶段补充。

### 下一步

支持多个 Agent 配置文件的发现和加载，然后再把 `agent_id` 接入会话隔离。

## 2026-08-20：阶段 1 补充，多 Agent 配置和隔离基础

### 做了什么

- 支持扫描 `configs/agents/*.json`，按 `agent_id` 加载多个 Agent。
- 重复的 `agent_id` 会直接报错，避免两个 Agent 配置互相覆盖。
- SQLite 的 `sessions` 表增加 `agent_id`，旧数据库会自动补默认值 `ecom-default`。
- 新增登录后的 `GET /agents`，可以查看当前可用 Agent 的基本信息。
- `/sessions` 和 `/chat` 支持传入 `agent_id`。
- 同一用户在不同 Agent 下使用不同会话，不能把一个 Agent 的会话拿给另一个 Agent 继续使用。
- RAG 工具支持按配置使用不同目录下的 `index.json`；默认 Agent 仍使用原来的 `data/index.json`。

### 为什么这样做

只把名字和 Prompt 配置化还不够。如果会话和知识库仍然全局共用，用户切换 Agent 后会串上下文或查到别人的知识。现在先把隔离边界建立起来，后面再做上传和管理页面。

### 遇到的问题和解决方法

- RAG 自定义工具第一次测试时仍然调用了全局 Retriever，导致自定义 Agent 查到了默认知识库。
- 已把检索逻辑改为使用传入的 Retriever，并让自定义索引延迟加载，避免 Agent 启动时就因为索引不存在而失败。

### 验证结果

- 配置目录、重复 ID、Agent 列表 API、会话隔离和 RAG 隔离测试均通过。
- 全部测试共 54 个，通过。
- `compileall` 通过。

### 当前状态

基础多 Agent 隔离完成。现在可以通过新增 JSON 配置创建不同 Agent，但还不能通过页面上传配置和知识库。

### 下一步

做知识库管理：先支持 Markdown 文件的安全校验、切片和索引输出，再接上传 API。

## 2026-08-20：阶段 5 前置，知识库处理模块

### 做了什么

- 新增 `agent/rag/knowledge_base.py`。
- 只接受 `.md` 文件，限制默认大小为 2 MB。
- 拒绝不存在、空文件和包含空字符的文件。
- 统一执行 Markdown 切片、`chunks.json` 保存和向量索引生成。
- 自定义 Agent 可以把索引输出到自己的知识库目录；默认电商 Agent 继续使用 `data/index.json`。

### 为什么这样做

上传接口只负责接收文件，文件校验和索引流程应该放在独立模块里，命令行、API 和后续异步任务都可以复用同一套逻辑。

### 遇到的问题和解决方法

- 知识库路径不能只影响 Prompt，还必须影响真正的 Retriever 和索引文件。
- 已让检索工具按 Agent 配置延迟加载对应索引，避免不同 Agent 共用默认索引。

### 验证结果

- 新增知识库校验和索引测试 3 个，通过。
- 全部测试共 57 个，通过。
- `compileall` 通过。

### 当前状态

知识库处理模块完成，但还没有暴露上传 API；当前不会改变线上已有知识库文件。

### 下一步

把 Markdown 上传接到管理员 API，并增加文件名、大小和构建失败的错误响应。

## 2026-08-20：阶段 5，管理员知识库上传

### 做了什么

- 增加 `GET /admin/agents/{agent_id}/knowledge`，查看文件列表和索引是否就绪。
- 增加 `POST /admin/agents/{agent_id}/knowledge`，管理员可以上传 Markdown 文件。
- 上传接口限制 UTF-8、`.md` 后缀和 2 MB 大小。
- 拒绝路径穿越、同名覆盖和普通用户上传。
- 上传后自动执行切片和索引构建。
- 索引构建失败时删除本次新文件，避免留下未进入索引的文件。
- 使用 `python-multipart` 支持 FastAPI 文件上传。

### 为什么这样做

知识库上传必须是完整流程：文件进入系统后要能校验、保存、切片和向量化。权限和失败回滚也要在第一版就有，不能让任何用户直接修改共享知识库。

### 遇到的问题和解决方法

- 文件上传依赖 multipart 解析，项目原来没有对应依赖。
- 已通过 `uv add python-multipart` 加入项目依赖，并更新锁文件。

### 验证结果

- 新增知识库 API 测试 3 个，通过。
- 全部测试共 60 个，通过。
- `compileall` 通过。

### 当前状态

管理员已经可以上传 Markdown 知识库并触发索引构建。删除、重新索引和异步任务还没有完成。

### 下一步

增加知识库文件删除和手动重建索引接口，再处理配置和数据库的版本管理。

## 2026-08-20：阶段 5 补充，知识库维护

### 做了什么

- 增加管理员手动重建索引接口。

- 删除后自动重建剩余文件的索引；删除最后一个文件时清理索引文件。

知识库上线后一定会修改。只有上传没有删除和重建，管理员无法修正错误文档，也无法处理索引失败。

- 业务层仍保留文件名校验，测试同时覆盖 400 和路由层 404 两种安全结果。

## 2026-08-20：阶段 6 前置，Agent 配置管理

### 做了什么

### 遇到的问题和解决方法

- Agent ID 最终会成为配置文件名，直接接受任意字符串会有路径穿越风险。
- 已在配置模型层限制格式，并在更新接口再次检查路径 ID 和请求体 ID。

## 2026-08-20：阶段 4 前置，SQLite 可靠性和容器持久化
